# 윤문·디자인 AI 티 규칙 감사 (herdr-team 0.7.0 기준, 2026-11-16, 읽기 전용)

## 0. 결론 요약
- "윤문 스킬"은 없다. 있는 것은 (a) 쓰는 쪽이 따를 규칙 문서, (b) 리뷰 시점의 정규식 경고, (c) 보고서 자기 점검 소절이다.
- 쓰고 난 글을 규칙대로 다시 고쳐 쓰는 독립 단계(윤문 패스, 별도 에이전트·스킬)는 없다. 설계가 일부러 뺐다(설계 16장 4단계 범위 밖: "문구 독립 스킬, 문구 전담 직무(writer), 자동 윤문, 맞춤법 검사기 연동", 줄 2857; p4 계획 줄 4603).
- 실사용(comment-browser)에서 규칙은 "적용되고 있다". 프롬프트 주입 55/62, 보고서 `### 문구 점검` 19/28. 결과물 문구는 규칙을 잘 지켰다.
- 약한 고리: 리뷰어가 문구 내용을 지적한 사례가 사실상 0건이고(형식 누락 지적만 있다), 자동 검사는 시안 HTML 에서 오탐이 많다. 상용구 오류 문구("문제가 발생했습니다")는 그대로 통과했다.

### 흐름(누가 언제 무엇을 하나)
1. planner: 인터뷰에서 문체·라벨·용어를 정해 voice.md 작성(확정 질문에 용어집 표 포함).
2. designer/developer: 작성 중 text-rules 를 읽고 "규칙에 어긋나면 고친 뒤" 보고서 `### 문구 점검` 에 적는다. 고치는 행위는 작성자 자기 점검이다.
3. `hteam review`: 태스크가 추가한 줄만 textlint 로 훑어 경고를 `## 문구 기준` 아래에 넣는다. 조건은 text-rules 파일 존재 + 바뀐 파일에 문구 대상 1개 이상.
4. 리뷰어(Codex): 경고를 열어 보고 §5 로 P1/P2/P3 판정. 보고서 소절이 있는지·맞는지 본다.
- 강제력: P1 만 REQUEST_CHANGES. 문구 P1 은 정책 문서 의무·권한 변경, i18n 변수 손상, 사실·수치 불일치, §2 확정 오류로 좁다. "AI 티(§4 항상 고친다)"는 P2 라 병합을 막지 않는다.

### textlint 가 잡는 것(실측 코드)
오탈자 15개 낱말, 이중피동, "에 있어(서)", 상투어(혁신적·획기적·최적의·극대화·차세대·시너지·패러다임·게임 체인저·seamless·empower), 메타 hedging 4개 구문, 챗봇 잔재 5개, 쉼표 3종(문두 접속어, 연결어미 뒤, "~고,"), 용어집 금지 표기, 한 파일 안 하십시오체/해요체 섞임.
못 잡는 것: "A가 아니라 B" 대구 횟수(규칙은 있고 검사는 없음), 형식명사 "것", "~를 통해/에 대해" 반복, "-들", 영어 병기, 상용구 오류 문구, 문장 길이·리듬 단조, 한 문서 안 같은 문장 틀 반복, 높임 호칭·서술어 불일치, 라벨 형태(저장/저장하기) 혼용, 오류 문구가 할 일을 알리는지.

## 3. 틈과 실패 사례

### 3.1 규칙이 막지 못한 문구
1. 상용구 오류 제목이 그대로 통과: `android/app/src/main/res/values-ko/strings_comments.xml:80` `comments_state_defect` = "문제가 발생했습니다". 같은 문구가 iOS `ios/CommentBrowser/DesignSystem/Gallery/DesignSystemGallery.swift:298`, `DesignSystemGallery.kt:382`에도 있다. text-rules §3.4 는 "무엇이 잘못됐는지"를 요구하는데 이 문구는 아무것도 알리지 않는다. P2 후보였으나 지적 0건.
2. "잠시 후 다시 시도하십시오." 가 Android ko 문자열 11곳에 복사돼 있다(`strings.xml:35,37,43`, `strings_comments.xml:74,79,141`, `strings_library.xml:34,54,55,57`, `strings_settings.xml:60`). 구체적 사정(연결 실패/보안 연결/저장 공간)은 앞 문장이 달래지만 끝맺음이 전부 같다. 상투 구문 반복을 보는 검사가 없다.
3. 정책 문서 `shared/comments/legal/terms.ko.md` 는 "있습니다/것입니다/때문입니다" 20회, "~할 수 있습니다" 다수. 정책 문서는 §1.3 보존 때문에 건드리지 않게 돼 있어 맞다. 다만 `guidelines.ko.md` 는 같은 이유로 쉼표 지적(P3)만 나왔고 가독 개선은 안 나왔다.
4. `docs/design/system/README.md` 같은 비대상 문서는 범위 밖이라 윤문되지 않는다. 사용자에게 보이지 않는 내부 문서이므로 의도다.

### 3.2 자동 검사 문제
1. 시안 HTML 은 한 줄이 수천 자인 단일 줄이다. 경고 위치가 `index.html:1465` 같은 줄 번호 + 앞 60자뿐이라 어디가 문제인지 열어 봐도 못 찾는다. 예: `comments/index.html:1465` 번역투 "에 있어" 경고의 발췌문은 `</div></div><div class="cb-toolbar">…` 이다.
2. 해요체 섞임 오탐: `comments/index.html:781` "해요체 56줄, 하십시오체 65줄". 해요체 줄은 시안에 넣은 가짜 사용자 댓글("뚝섬은 주말 밤에 사람이 정말 많아요.")이다. 사람의 댓글 예시는 서비스 문구가 아닌데 같은 경고가 T-008 r1·r2·r5 에서 라운드마다 반복됐다.
3. 쉼표 경고 "고," 는 설명문(보드 소개 글)을 많이 잡는다. 시안 9화면을 전체 줄로 돌리면 화면당 2–12건이다. 리뷰어에게 신호 대 잡음이 낮다.
4. 규칙은 있고 검사는 없는 항목(위 1절 "못 잡는 것"). 특히 "A가 아니라 B" 2회 이상, "~를 통해" 3회 이상 같은 반복 조건은 코드로 쉽게 셀 수 있다.
5. 경고는 문구 대상에서 `docs/design/*.md`, `docs/design/system/**`, `notes.md` 를 뺀다. 디자인 시스템 README 의 "문구" 절도 사용자에게 보이는 문구는 아니라 맞다.

### 3.3 프로세스 틈
1. 윤문의 실행 주체가 작성자 한 명이다. 같은 에이전트가 쓰고, 자기 규칙으로 점검하고, 보고서에 "지켰다"고 쓴다. 독립된 재작성·검증 패스가 없다.
2. 리뷰어가 문구를 인용하지 않아도 되는 형식이다. `review-text.md` 는 "이 태스크가 바꾼 텍스트만 지적"만 말한다. 리뷰 파일에 "읽은 문구 N줄" 같은 증거 칸이 없어서 문구를 실제로 읽었는지 알 수 없다. 62개 리뷰 중 문구 내용 지적은 1건.
3. 보고서 소절 누락이 반복된다(T-012, T-017, T-023 모두 리뷰가 P2 로 잡았음). 즉 지침만으로는 누락이 생기고 리뷰가 후행으로 잡는다. 소절 유무는 `hteam report` 단계에서 기계적으로 검사할 수 있다.
4. `### 문구 점검` 내용이 "서비스 문구는 쓰거나 바꾸지 않았다" 한 줄이어도 통과한다(T-009 r3). 사실이면 맞지만 확인할 증거가 없다.
5. voice.md 가 없는 프로젝트(shop)는 종결체 통일만 본다. 용어집 검사·라벨 형태 검사가 꺼진다.
6. 문구 P2(AI 티)는 REQUEST_CHANGES 사유가 아니라 후속이다. 상투어가 들어가도 병합된다.
7. 디자인 §1 은 "정해진 틀 같은 랜딩", "가운데 정렬 반복", "카드 모서리 반복", "회색 남발"처럼 판단이 필요한 항목이 많고, lint.py 는 이모지·왼쪽 줄·파랑·보라 그라디언트·확대 막기·포커스 제거 정도만 기계적으로 본다. 사진·시안 전체의 "생김새 단조로움"은 리뷰어가 렌더해서 보는 수밖에 없다.

### 우선순위 의견
1. 즉시(작음): 3, 9, 1. 문서만 고치면 된다. 리뷰·작성 증거가 남는다.
2. 다음(중간): 4, 5, 6. 코드와 시험이 든다. 기존 오탐을 줄이면서 규칙-검사 불일치(대구, 반복 구문)를 메운다.
3. 사용자 결정 필요: 2(독립 윤문 스킬)와 7(문구 P2 차단). 둘 다 설계 16장 범위 밖 결정을 바꾼다. 윤문 스킬은 im-not-ai 의 다단계 실행기를 참고하되 §1 보존·과교정 가드를 우선하는 구조가 안전하다.
4. 먼저 `docs/superpowers/specs/` 11.7 에 "윤문 = 규칙 + 경고 + 자기 점검. 자동 재작성은 없음"을 한 문장으로 못박으면 기대 불일치를 줄인다.

## 5. 한계
- 텍스트 샘플링은 정규식 기반이다. 사람이 읽고 AI 티를 판정한 것이 아니다. "AI 티 없음"은 "정규식으로 안 잡힘 + 표본 문구가 구체적"이라는 뜻이다.
- 리뷰 파일 키워드 분류(문구·§1)는 단순 매칭이라 누락·과다가 있을 수 있다. 문구 P1/P2 가 사실상 0건이라는 큰 그림은 수동 확인한 목록과 일치한다.
- comment-browser 보고서 28개 중 T-0xx 번호 사이 빠진 태스크(022, 024 등)는 보고서가 없거나 다른 상태다.
- 원격 기기의 사용 프로젝트는 보지 않았다. 어떤 파일도 고치지 않았다.
